## endpoints-01

### Finding

- **Recovery endpoints duplicate the shared JSON response primitive.** `app/src/endpoints/recovery.ts:112-116` defines a local `json(body,status)` that is byte-for-byte equivalent to `app/src/endpoints/respond.ts:101-110`'s exported `json` when no extra headers are supplied. All seven recovery operations use it. This creates one local response implementation that can drift in content type or serialization defaults. Smallest safe change: import `json` from `./respond` and remove the local helper. Preserve the current status/body values and default 200 behavior; no recovery authorization, response contract, transaction, or error behavior changes.

### Rejected / not findings

- `recoveryParse.ts` and `previewParse.ts` both parse large untrusted content, but recovery accepts JSON with absent body → `{}` and an exact 4 MB declared-length guard; preview requires multipart `data`, guards whole-body framing then measures UTF-8 bytes of the field, and returns different 400/413 messages. Their caps are explicitly independently chosen. Do not combine them with `readJsonBody`.
- `forgotPassword.ts` has a separate body read/16 KiB bound; `respond.ts` explicitly documents its stricter parsing and independent stable copy. Its uniform response and non-SMTP branch make consolidation behavior-sensitive.
- `markMessagesRead.parseIds` accepts/coerces a bounded id array; discussion read ranges require safe-integer JSON numbers; redaction accepts only literal booleans. These are distinct wire contracts, not duplicate validators.
- `previewVersion`'s shared `resolveUnsavedEffective` and `previewShared` already own the common auth/split/render/response paths. The saved GET, unsaved HTML POST and PDF POST have materially different output, rate/concurrency and caching behavior.
- Export kind/tag parsers share the query-reading primitive locally, but validate different query keys, optionality, messages, and types; no useful extraction beyond the existing `parseFormat.ts` module.
- Forum moderation endpoint actions already share `moderate` for transaction, lock order, reauthorization, post-commit logging and `noRowsReason`; per-action SQL stays distinct because topic redaction can target subsets, reply redaction cannot, and delete/pin use Payload hooks.
- Version export handlers already reuse `authorizeVersionExportRequest`; serve-only downloads, prepare, and status intentionally differ in rate charging, cache/job binding, bytes vs JSON and error states.

## generator-01

**Source-confirmed candidate:** the saved-version HTML section cache and compare-diff cache independently implement the same per-key single-flight lifecycle: check the in-flight map, return the extant promise, register a newly started compute, then delete the map entry in `finally` after either success or rejection. A small generic `withSingleFlight(map, key, work)` helper would keep the rejection cleanup rule in one place, avoiding the especially costly drift where one failed render leaves a rejected promise pinned and future requests never retry. Leave each module's cache read/decode, logger, computation, and cache write in place. Preserve one map per cache/key namespace, the same promise result/error propagation, and `finally` deletion on both outcomes. No null or permission behavior changes: authorization remains at callers, and existing cache read/write fallbacks remain independent.

Do not merge their rendering/diff algorithms or bypass `renderVersionSectionsCached` from diff. `proseLinks.ts` and `fieldSplit.ts` intentionally maintain paired lists for different generator-vs-editor contracts, and `lessonSequenceProseHyperlinkTargets` is a separate fidelity oracle; merging their walks would risk weakening that check. Repeated `withParenthesizedProseLinks` calls in individual DOCX builders are not a confirmed extraction: per-deliverable APIs are independently callable and output fidelity is sensitive, while the traversal gain has no demonstrated material impact. Vendor remains pristine.

## jobs-01

**Source-confirmed candidate:** four task handlers repeat the same failure sequence: structured `logger.error`, `captureException` with task-specific context, then rethrow the same error. Exact sites: `app/src/jobs/generateVersionArtifact.ts:89-95`, `emailVersionArtifact.ts:108-117`, `messagePing.ts:81-87`, `passwordResetEmail.ts:89-95`. A small shared `reportAndRethrowJobError` helper could own that sequence while accepting each caller's logger context, message, and tracker context. The concrete maintenance benefit is keeping the observable failure contract together; password-reset's comment already calls out a consistency gap with the other jobs. Preserve each log message and exact fields, each distinct safe tracking context, synchronous capture followed by rethrow of the original error, and each existing catch boundary (password reset catches send failures only; the other listed handlers catch their broader handler body). Do not unify retry counts (`passwordResetEmail` retries three times; artifact/message jobs use zero) or no-op missing-row branches. This helper must not change transactions or swallow errors.

**Rejected extractions:** `expireEditRecovery.ts` intentionally captures and rethrows without Payload structured logging; `prewarmVersionArtifacts.ts` intentionally logs/captures but swallows because prewarming is best effort. Neither belongs in the rethrow helper. The artifact/email tasks share cache/generation seams already through `exportArtifacts.ts`; their warm-cache and always-generate paths differ by design. `messagePing` validates message existence before send; version jobs use different missing-row behavior and inputs.

**Coverage:** fully read all 6 assigned implementations: `app/src/jobs/emailVersionArtifact.ts`, `expireEditRecovery.ts`, `generateVersionArtifact.ts`, `messagePing.ts`, `passwordResetEmail.ts`, `prewarmVersionArtifacts.ts`.
