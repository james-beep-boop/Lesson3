### Finding — batched locked ancestry-history read for multi-plan imports

On the web upload path, `writePrepared` first resolves each prepared item's target plan under subject-grade locks (`app/src/ingest/index.ts:825-835`), locks all existing plans, then `releasePreview` reads all plans and their release metadata in two queries regardless of file count (`:845-849`, helper `:385-417`). The subsequent serial loop makes a separate unpaginated history `payload.find` for every revised existing plan (`:875-887`) to obtain `semver`, author, source and merge parent, and `meta.substrand_id`; each result is then mapped and scanned by `latestRelease` (`:888-897`) before creating that version. In a batch touching N existing plans this is N sequential history queries within the one write transaction (up to 500 incoming JSON files by the upload cap), plus the two fixed release-preview reads. It loads all history rows for each plan separately even though the plan set and the shared plan/version history scan are already known under the same locks.

Minimal safe direction: keep the post-lock `findExistingPlan` re-resolution and all row locks intact. In the locked upload path, expose the selected per-plan history from `releasePreview` (or issue one batched history read for all locked `existingPlanId`s) with the extra ancestry projection fields `author`, `sourceVersion`, `mergedFrom`, and `meta.substrand_id`; group by plan id and call the same `latestRelease` for each item. This changes N sequential history lookups to one set lookup for the same locked plan IDs while retaining each plan's exact full history and existing release-selection predicate. For efficient loading, prefer making the one under-lock release-history query carry both projections and pass grouped history onward, with the ancestry-only fields requested only in the write phase so the read-only confirmation phase does not fetch them. Preserve per-file decision order, `latestRelease`, all transaction boundaries, and release conflict semantics. Validate with re-ingest integration cases for predecessor choice (including teacher patch not selected), multiple plans in one upload, no existing plan, and release confirmation changed between preview/write; add a query-count assertion for multi-plan write preparation if the existing fixture setup can do that without brittle SQL introspection. No live/database tests were run.

This is a measured-source candidate, not a claim of observed production latency: each current query is explicit and serial, and the upload accepts up to 500 files, but typical batch size and historical rows per plan were not measured. For one-plan imports this does not reduce query count (and the existing current path is simple); prioritize only if multi-plan imports are a real workload.
