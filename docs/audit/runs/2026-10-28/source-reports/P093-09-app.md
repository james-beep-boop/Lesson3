**C2. Transient verify failures shown as "invalid or already used". Confirmed local reasoning on the copy. Low to medium.**
- Evidence: `VerifyEmail.tsx:25-26` maps every non-OK response and every fetch rejection to `'failed'`. Lines 37-42 then say the link "is invalid or was already used." The header at `:4-7` says the token is nulled only on success.
- Precondition: the verify POST fails with a rate-limit, a 5xx, or a network error while the token is still valid. Policy states the verify endpoint is rate-capped, so this is reachable. The specific status code is unverified.
- Expected: a failure that did not consume the token should not claim the link is invalid or used. The exact replacement copy is not specified by policy, so I am not inventing it.
- Actual: the used/invalid message, which also directs the user to sign in.
- Reproduction: mock `fetch` to resolve `{ ok: false, status: 429 }` (and reject separately), then assert the text does not contain "invalid or was already used".

**C3. Token prop change ignored after mount. Lead, low.**

- Reproduction: render with token A, rerender with token B, assert `fetch` was called with B.
