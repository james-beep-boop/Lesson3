**Candidates**

1. **Medium — confirmed local reasoning; user impact depends on unseen call sites.** `app/src/lib/formatDate.ts:8,11`. The docblock (line 5) says fixed formatting means server and client "cannot disagree". `dayFmt` sets a locale but no `timeZone`, so the runtime default zone decides the day. Precondition: a timestamp near midnight UTC. Expected: identical output everywhere. Actual: `formatDay('2026-10-27T23:30:00Z')` gives "27 Oct 2026" under `TZ=UTC` and "28 Oct 2026" under `TZ=Pacific/Auckland`. Reproduction: format the same instant in two processes with different `TZ` and compare. Whether this causes a hydration mismatch depends on whether any call site renders during SSR.

2. **Medium-low — lead.** `app/src/lib/identity/installationId.ts:24-25, 30-42`. `readInstallationId` turns any read error into `null`. With `apply=true`, a failed read can therefore return `{previous: null, current: null}` with no error. The function also never checks that `current !== previous` after the update. Precondition: `findGlobal` throws, or the update is a silent no-op. Expected: the failure is distinguishable or thrown. Actual: the result looks like an ordinary "no ID" outcome. Reproduction: stub `findGlobal` to throw and call with `apply=true`; separately stub `updateGlobal` as a no-op. The caller in `scripts/reset-installation-id.ts` is not in range, so its handling is unknown.

3. **Low-medium — lead, reachability unverified.** `app/src/lib/editorGroups.ts:199-202`. The comment says the roster includes "anyone who holds a role here but is NOT grantable". The loop adds only `subjectAdminIds`, not `editorIds`. If a site admin (excluded from the roster) holds an `editor` assignment, `groups[].editorIds` contains an ID absent from `roster`, which renders as a blank entry. Reproduction: fixture a site admin with an `editor` assignment and assert every `editorIds` entry appears in `roster`. Whether such an assignment can exist depends on `access/index.ts` and `userRoles`, which are not in range.

4. **Low — unverified.** `app/src/lib/firstUserBootstrap.ts:41-42`. Suppression assumes `disableVerificationEmail` only skips the mail. Nothing in range shows `_verified` is still set. The docblock (line 26-27) says Payload marks the user verified after sending the mail. Reproduction: empty database, first-register with `overrideAccess`, then assert `_verified === true`.

5. **Low — lead.** `app/src/lib/emailLinkBase.ts:9`. If neither `ADMIN_URL` nor `SERVER_URL` is set, the base is `''` and reset/verification links become relative. Nothing in range fails closed. A boot guard may exist elsewhere.

6. **Low.** `app/src/lib/env.ts:15-16`. `Number()` accepts `0x10` (16), `1e3` (1000) and `" 7 "` (7), while the docblock says "positive integer". Likely acceptable, but the behavior differs from the documented intent.
