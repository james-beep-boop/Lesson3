## Purpose and invariants (as stated in the files)

- **Reset form:** posts token and new password to Payload's reset endpoint. Branches on an error code, not status or message text, so a disabled account's valid link gets its own message. Removes `?token=` from the address bar after mount.

- **Signup page:** `emailEnabled` is `!!process.env.SMTP_HOST?.trim()`.

## Candidates

**C1: Misleading error copy from message-text matching. Low. Lead, partly confirmed.**
`SignupForm.tsx:43-44`. Any non-429 server message matching `/email/i` is replaced with "An account with this email may already exist — try signing in instead."
- Precondition: the server returns a non-duplicate validation error whose text contains "email" (for example, a malformed address).
- Expected: the server's specific message, or a generic failure.
- Actual: the duplicate-account hint is shown.
- The branch is confirmed from the source. Whether the server actually returns such text is unverified.
- Test: stub `fetch` to return 400 with `{errors:[{message:'Email must be a valid email address'}]}`, submit the form, and assert the alert does not contain "may already exist".
- The file's own reset form says to branch on codes, not message text, so this is inconsistent with the file's stated approach.

**C2: Unsupported retry-window copy. Low. Lead.**
`SignupForm.tsx:42`. The fallback for HTTP 429 reads "please try again tomorrow", implying a 24-hour window. The supplied policy says signups are capped per address and site-wide but gives no window.
- Precondition: a 429 with an empty message body.
- Actual: the copy asserts a daily reset that the policy does not define.
- Cannot confirm a mismatch without the cap configuration. Do not treat the wording as policy until the window is stated.

**C3: Success copy may outrun actual email delivery. Unverified lead.**
`SignupForm.tsx:60-64` chooses "we've emailed a verification link" from the `emailEnabled` prop. `signup/page.tsx:21` derives that prop only from `SMTP_HOST` being non-empty.
- Precondition: `SMTP_HOST` is set but sending fails, or the sender is misconfigured.
- Expected: no claim that an email was sent unless Payload's verification send succeeded.
- Actual: the claim is shown unconditionally in that mode.
- Whether a failed send surfaces as a failed create depends on Payload behavior that was not supplied.

**C4: Non-disabled error collapsing. Low. Lead.**
`ResetPasswordForm.tsx:72-74` maps every non-OK response other than the disabled code to "invalid or has expired." If the reset endpoint returns 429 or 5xx, the user is told their link is bad.
- Precondition: a rate-limit or server error from the reset endpoint.
- Whether such responses exist is unknown from the supplied text.
