## Purpose and invariants

- **rateLimit.ts:** Fixed-window counters in Postgres via one UPSERT per hit. Keys are `${bucket}:${key}`. Denials return 429 with `Retry-After`.
- **readBundle.ts:** Caller-scoped reads. `null` is returned only for 403/404. The version list is the read-proof for system reads.
- **relId.ts:** Validates ids as integers in 1..2³¹−1. Digit strings are accepted.
- **renderTimings.ts:** Env-gated phase timings. Disabled mode is a no-op.
- **requestedVersion.ts:** Maps a URL version id to `absent`, `found`, or `unavailable`, and never substitutes a different version.

## Candidates

**C1 (low, confirmed local reasoning): non-monotonic window can reset a counter.**
- Evidence: `rateLimit.ts:211` stamps `windowStart` from `Date.now()` taken before the query. `rateLimit.ts:216-217` then overwrites `window_start` unconditionally, and resets `count` to 1 whenever the stored window differs. A stale-stamped statement that commits after a newer one moves the window backwards and restarts the count.
- Precondition: concurrent hits for one key whose timestamps straddle a boundary, or replicas with clock skew (`rateLimit.ts:12`).
- Expected: at most `max` admissions per window, plus the boundary tolerance documented at `rateLimit.ts:15-18` (about 2×, across a boundary).
- Actual: one window admits more than the documented bound. Each stale write adds another `max`.
- Reproduction (Postgres integration test, `take(db, 'k', {max: 2, windowMs: 1000}, now)`): call with `now=1500` twice (both allowed), then `now=900`, then `now=1500` three times. Expected: 2 admitted in `[1000,2000)`. Actual: 4 admitted (the 6th call is denied).
- Likelihood depends on pool latency; not measured.

**C2 (unverified lead, high impact if true): schema assumptions.**
- Evidence: `rateLimit.ts:212-218` requires a unique constraint on `bucket_key` for `ON CONFLICT`, and a 64-bit `window_start`. Current epoch-ms values exceed the int4 maximum.
- Expected: the migration defines both. Actual: unknown, since the migration is not in range.
- Settle by: reading the migration and running the UPSERT once against a fresh database.

**C3 (low, diagnostic integrity): `renderTimings.ts`.**
- Evidence: `renderTimings.ts:54` overwrites `phases[label]`, so a repeated label keeps only the last duration. `renderTimings.ts:59` spreads `context` after `route` and `totalMs`, so a context key can silently override them.
- Reproduction: `time('q', 10ms)` then `time('q', 20ms)` gives `phases.q = 20`.
- Expected: not specified in the module. The overwrite behaviour is inferred, so this is an uncertain lead, not a confirmed defect.
