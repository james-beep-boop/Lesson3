## Purpose and invariants

- **lineage.ts:** Builds bounded ancestry (`MAX_LINEAGE` = 2000) from `sourceVersion` and `mergedFrom`. Stamps it on every create and rejects parents from a different lesson plan.
- **outcome.ts:** Reports which side's content is already contained in a clean merge result. Ancestry alone is not treated as proof.
- **compareGroups.ts:** Splits rendered documents into groups. Totality: every top-level node lands in a group. Uniqueness: duplicate keys throw. Also merges key sequences.
- **conversionLimit.ts:** Non-blocking in-process concurrency bound. Releases its slot in `finally`.
- **discussionComposer.ts:** Pure submission state machine. The submission key travels with its content. An uncertain attempt locks the fields until a post settles it.

## Candidates

**C1. Medium (lead, local return value confirmed). `app/src/lib/discussionComposer.ts:103-111`**
`classifyCreateStatus(0)` returns `'refused'`. The header at `:99` defines `'uncertain'` as "the server failed or the answer never arrived". A transport failure with no HTTP status is a case where the answer never arrived.
- Precondition: the unseen caller maps a network failure to status 0 and feeds that result through this function.
- Expected: `'uncertain'`, so fields stay locked and "Try again" reuses the same key.
- Actual: `'refused'`. With nothing unresolved, the reducer returns to `editing` and unlocks the fields while keeping the key.
- Consequence: if the first request actually committed, an edit made after the unlock and resubmitted under the same key is recovered as the original post. The edit is silently dropped, which is the hazard the header at `:8-11` describes.
- Repro: `expect(classifyCreateStatus(0)).toBe('uncertain')`. Then check that a `submit` followed by a `refused` event leaves `fieldsLocked(state) === true`, given the caller's status mapping.
