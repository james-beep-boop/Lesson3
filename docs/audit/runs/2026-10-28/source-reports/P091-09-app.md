**C1 — Low severity, confirmed cascade reasoning; reachability unconfirmed**
- **Location:** `styles.css:971-977` (hover and focus-visible fill) against `styles.css:978-981` (`.share-menu button:disabled`).
- **Precondition:** A `<button disabled>` inside `.share-menu` that is not a `.btn`. I have not checked whether any caller renders one.
- **Mechanism:** `.share-menu button:hover` and `.share-menu button:disabled` both have specificity 0-2-1. The disabled rule comes later and sets only `color` and `cursor`. It does not reset `background`, so the `--bg-soft` hover fill still applies. The `.btn` system avoids this at 1173-1182, but the share-menu path has no equivalent rule.
- **Expected:** The file's own intent at 1164-1166 is that unavailable controls do not light up under the pointer. I am applying that intent by analogy to share-menu items, since no share-menu policy is documented.
- **Actual:** A disabled share-menu item takes the hover fill.
- **Focused reproduction:** Playwright, with the stylesheet loaded and a fixture `<div class="share-menu"><button disabled>Email</button></div>`. Hover the button, then assert `getComputedStyle(el).backgroundColor` is transparent (`rgba(0, 0, 0, 0)`). Expect failure on the current CSS. Native disabled buttons cannot take focus, so the hover path is the only one that matters here.
