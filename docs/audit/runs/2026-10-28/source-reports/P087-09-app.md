## Candidates

**1. `sendMessage.ts:28-31`: lone `version` is silently dropped. Confirmed local reasoning. Low-medium.**
- Precondition: a caller passes `version` with no `lessonPlan`.
- Expected, per the file's own comments (lines 6, 12): the rule is that the server rejects a lone version, so the caller should see an error.
- Actual: the guard at line 29 strips `version`, the request succeeds, and the message is sent with no lesson context and no error.
- Repro (Vitest, stubbed `fetch`): call `sendMessage({ recipient: 2, body: 'x', version: 9 })`. Assert the request body has no `version` key and the promise resolves. Expected: rejection, or a request the server rejects. The "expected" side comes from the in-file comment, not confirmed product policy.

**2. `messages/page.tsx:147-153`: fallback reference uses a populated plan title, which the comment says is viewer-scoped. Lead, unverified. Security-relevant.**
- Line 266 says references are "resolved in one viewer-scoped batch". The fallback at lines 147-153 instead reads `m.lessonPlan.title` from a `depth: 1` populate, using `overrideAccess: false` on the message query.
- Whether Payload applies read access to populated relationship documents is unverified. If it does not, a recipient can see the title of a plan they cannot read.
- Repro: recipient not entitled to plan P receives a message with `lessonPlan: P` and no resolvable version. Render the page and assert P's title does not appear. Expected: per the line 266 comment.

**3. `messages/page.tsx:136-150`: positional alignment of `versionReferences[i]` with `messages[i]`. Lead, unverified.**
- References are matched by array index. If `resolveVersionReferences` returns a shorter or reordered array, a card can show another message's version label. Line 149 then masks the mismatch with `??`.
- Repro: mock the resolver to return a shorter array or reversed order. Assert each card's label matches its own message. The resolver's order contract is not in the supplied range.

**4. `messages/page.tsx:283-286`: timestamps use server timezone. Lead, unresolved.**
- `toLocaleString('en-GB', …)` has no `timeZone`, and this is a server component, so times follow the server process timezone rather than the reader's. Other parts of the policy talk about reader-local days (`LocalDay`), but nothing states the expectation for messages.
- Repro: render with `TZ=UTC` and `TZ=Pacific/Auckland` and compare. Expected policy is needed before this is a defect.

**5. `messages/page.tsx:44-57`: unreadable `?plan=` is dropped without notice. Lead, low. Policy not stated.**
- If `?plan=` is unreadable and no version is requested, `about` becomes `null` and `missingVersion` stays `false`. The composer opens with no lesson link and no message. The comment only covers the version case.
- Repro: `GET /messages?plan=<unreadable id>`. Assert whether the composer shows a notice. Expected policy is unknown.

**6. `(frontend)/page.tsx:53-81`: plans with a null `officialVersion` are invisible. Lead, policy unknown.**
- Only plans with an Official pointer produce rows. A plan whose pointer is null, for example after an Official is deleted, disappears from the catalogue with no fallback or notice. Whether that state is reachable is outside the supplied range.
- Repro: plan with `officialVersion: null` and no favourites. Assert it appears in neither `rows` nor `pinnedRows`. Expected policy is needed.
