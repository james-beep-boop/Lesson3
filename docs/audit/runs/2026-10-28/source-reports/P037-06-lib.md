## Purpose and invariants (from the file's own comments)

- `start` is the only insert or reactivation path. It is one SQL statement, and resume on an active row is a no-op. Reactivation advances `generation`, resets content, and restarts the TTL clock. The active-capture cap counts only non-retired rows for the user.
- `capture` is a compare-and-set update of an existing active row, with preconditions evaluated inside the `UPDATE`. It projects the form document itself and enforces a 512 KiB ceiling on the projected content.
- `retire` is the one shared transition for save-as-new, discard, admin cleanup and expiry. It does not advance `generation`. The save-as-new path requires a transaction.
- Every statement runs on the request's transaction through `txDb`.

## Candidates

**No confirmed defects.** The file's comments and SQL agree on every path I could check locally, including resume at capacity, reactivation at capacity, the retired-row fencing, and the `updated_at` handling.

**Lead A (uncertain, low): capture clears stored Combine state when the client omits it.**
- Evidence: `kernel.ts:251-257` sets `context` to `null` when `combineContext` is missing or invalid. `kernel.ts:267` then writes `combine_context = ${context}::jsonb` on every capture, so a `null` overwrites a previously stored value.
- Precondition: a capture succeeds with a valid `combineContext`, then a second capture for the same active row omits it or sends an invalid value.
- Observed locally: `combine_context` becomes `NULL`.
- Expected: not determinable. The comment at `kernel.ts:255` ("Drop invalid optional metadata") suggests dropping invalid input is intended. It does not say whether a missing field should preserve the prior value.
- Repro test: start; capture with a valid `combineContext`; capture again with the same `formDocument` and no `combineContext`; assert the stored `combine_context`. Keep it as a question until the intended semantics are stated.

**Lead B (uncertain, low): the 512 KiB ceiling excludes `combine_context`.**
- Evidence: `kernel.ts:258-261` measures only `json`, the projected content. `kernel.ts:257` and `267` store `context` unmeasured.
- Precondition: a `combineContext` near the maximum that `parseCombineContext` accepts.
- Expected: unknown. The comment at `kernel.ts:183-189` says "serialised content", which may mean only the prose column. Whether `parseCombineContext` bounds size independently is in a file I did not read.
- Repro test: a valid form document plus a maximally large valid `combineContext`; check whether the row is written and whether the total stored size exceeds the stated ceiling.

**Not reported (documented carve-out):** the active cap is approximate under concurrency. Two `start` calls on different pairs at 19 active can both insert, because the `active` CTE takes its snapshot before either commit (`kernel.ts:124-141`, `172`). `kernel.ts:91-92` says "Approximate by design". The sentence points to `start`, but `start`'s comment does not explain the approximation. Treat this as an intentional carve-out, not a defect, unless the governing spec says otherwise.
