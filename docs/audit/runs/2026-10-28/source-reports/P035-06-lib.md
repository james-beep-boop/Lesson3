## Purpose and invariants (as implemented)

- **discussionPages.ts**: server reads that run as the viewer (`overrideAccess: false`). Pinned topics come from a separate query, not a sort key. Authors are projected names-only. Pages are derived from `discussionPaging`.
- **discussionPaging.ts**: pure pagination. Page k holds seqs `50(k−1)+1 … 50k`, and seq 0 is on page 1. `entryPage` opens at the page holding `lastReadSeq+1`, clamped. `markRangeFor` gives the contiguous range a page may mark read.
- **discussionText.ts**: LIKE escaping, the word-AND search value, and a linkifier that only links `http(s)` with a host and renders everything else as text.

I checked the pagination arithmetic at the boundaries (seq 0, 50, 51, 100, lastSeq 0, invited author at −1, read-through-all). Every case I traced gives the documented result, so I found no confirmed defect in `discussionPaging.ts`. `escapeLike` and `likeAllWords` are also consistent with their comments, and `linkify` only emits `http(s)` hrefs.

## Candidates

No confirmed defects in the supplied ranges. The following are uncertain leads. Each depends on code I did not see.

**C1: Unreadable author shown as "Deleted User"** (`discussionPages.ts:63-66`, `44-61`; severity: Low, unverified)
- Precondition: the topic or reply author exists, but the viewer cannot read that user under the `users` access rules, or `userDisplayName` needs a field outside `select: { name: true }`.
- Actual: `authorName` returns `DELETED_USER` for any id missing from the names map, so an existing author is labelled as deleted.
- Expected: not defined by the supplied material.
- Repro: fixture with a live author id, `users` read denied to the viewer, and an assertion on the label the page produces.

**C2: Null `lastReadSeq` coerced to 0** (`discussionPages.ts:267`; severity: Low, unverified)
- Precondition: a `discussion-participation` row whose `lastReadSeq` is null. This depends on the column's nullability, which I did not see.
- Actual: `Number(null)` is `0`, so the reader is treated as having read through the opening post. That changes `entryPage` and the marker that `markRangeFor` expects.
- Expected: not defined by the supplied material.
- Repro: a participation row with null `lastReadSeq`, then assert the `lastReadSeq` and entry page returned by `loadThread`.

**C3: Positional reference alignment** (`discussionPages.ts:291-318`; severity: Low, unverified)
- Precondition: `resolveVersionReferences` drops or reorders entries relative to `[topic, ...replies]`.
- Actual: `references[i + 1]` would attach a reference to the wrong reply, with no error.
- Expected: one entry per input, in order. I cannot confirm that contract from here.
- Repro: stub the resolver to return fewer entries for a page with a null reference, then assert each post keeps its own reference.

**C4: Bracket heuristic includes prose `)`** (`discussionText.ts:40-55`; severity: Informational, ambiguous)
- Input: `(see https://x.org/a(b)`. The candidate `https://x.org/a(b)` is linked, so the closing prose parenthesis becomes part of the URL.
- Actual: the trailing `)` is kept because the bracket count over the whole candidate balances.
- Expected: ambiguous. Whether this is a defect depends on a policy I was not given.
