## Leads (uncertain, not confirmed)

1. **MarkShownRead.tsx:18-29, low.** The `fired` ref latches after the first non-empty `ids`. If the same mount later receives a different `ids` (for example after `router.refresh()` from Composer or ReplyBox), no POST is made. The header (:15) says it marks "the inbox messages the server just rendered." Expected: a POST with the new ids. Actual: no POST, so new messages stay unread until a later mount. Proposed test: render with `ids=[1]`, rerender with `ids=[2]`, assert `fetch` is called with `{ids:[2]}`. Whether the parent re-passes new ids is outside this range.

2. **LoginForm.tsx:65, 72, low.** If `readErrorCode` throws on a non-JSON 429 or 503 body, the catch at :72 shows "Sign-in failed" instead of the busy message at :26-27. Proposed test: mock a `text/plain` 429 response and expect "Sign-in is busy". Depends on `readErrorCode`, which is not in range.

3. **LoginForm.tsx:19-20 and :35, low.** The comment asserts lockout returns 401. If lockout returns another status, the user gets "Invalid email or password." This needs the server contract to settle.

4. **Composer.tsx:37, 47 and ReplyBox.tsx:31, 40, low.** The double-send guard reads `busy` from the render closure. Probably benign because the button is disabled and discrete events flush. Proposed test: dispatch two submits in one tick and assert one send.

5. **Composer.tsx:44-45.** `version: about?.versionId` can be `null` (type at :22) and is forwarded unchanged. Whether the server accepts `null` is unknown.

6. **login/page.tsx:25.** The `emailEnabled` test is written inline, but the comment says it is the "same test" as the Sign up and Forgot password pages. Those pages are not in range, so divergence is unverified.

7. **Composer.tsx:98.** "Everyone is listed by name" depends on the roster source, which is not in range. Whether disabled or unverified accounts are excluded is unknown.
