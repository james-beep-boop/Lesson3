## Purpose and invariants (as stated in source)

- **versionsOrder.ts:** Pure comparator. The Official version sorts first, then `createdAt` descending. Unparseable or missing dates sort as 0.
- **welcomeDismissal.ts:** Single source for the per-user `localStorage` key for the Welcome dialog's "don't show again" state.
- **widgetUser.ts:** Builds the Editing-access widget payload. `email` is included unconditionally (documented SPEC §8 carve-out). `updatedAt` is the required freshness token. `userDisplayName` falls back to `User <id>` when there is no name.
- **wireError.ts:** Extracts `errors[0].message` from a failed REST response, falls back to `"<fallback> (<status>)"`, and maps 423 to a fixed lock message. It is documented as never throwing.

## Candidates

**C1 — Uncertain lead, Low. Blank name can yield an empty person label in the revoke confirmation.**
- **Evidence:** `widgetUser.ts:38-39` uses `u.name ?? \`User ${u.id}\``. `??` does not replace `""`. `toWidgetUser` (lines 87-94) passes that through. `personLabel` (line 52) returns `u.name` unchanged when `email` is absent.
- **Preconditions:** A user record with `name === ""` and no `email`. Whether this state is reachable depends on the `users` schema, which is not in the supplied range. The doc comment says email is optional and "a user record may genuinely lack an address".
- **Expected:** Unclear. The comment says "no `name`" gets the `User <id>` fallback and that destructive confirmations must identify people precisely. Neither says whether `""` counts as "no name". I am not inferring policy from the implementation.
- **Actual (local reasoning):** `personLabel` returns `""`. The grant picker and revoke dialog would then identify nobody.
- **Focused test (sketch):** `toWidgetUser({ id: 7, name: '', email: undefined, updatedAt: 't' })`, then assert `personLabel(...)` is non-empty. This test would fail today. Whether it reflects a defect depends on the answer to the open question below.

**C2 — Cosmetic-adjacent, not reported.** `personLabel` with an empty name and an email yields `" — a@b"`. This is a display nit and is not reported.
