# F-C42-002 — conversion body timeout loses its error category

- Fixed source: `6e75a173e822e4c4be42821b0a4af48ca457bd36`.
- Severity: Low; error classification and diagnostics.
- Evidence: actual Node 24 HTTP fetch against a local fault server; endpoint mapping source-traced.
- Review: Haiku P048 → Sol source/runtime critique → fresh-context Haiku response → Sol scope check.
- Status: audit only; no implementation change.

`app/src/generator/docxToPdf.ts:59–70` wraps a fetch rejection in `PdfConversionError`, but reading the successful response body at line79 is outside that try. A sidecar that returns success headers and then stalls causes a raw TimeoutError. `previewVersion.ts:211–217` classifies that as a generator/render failure (500), rather than a converter failure (502).

`app/tests/audit/service-errors.ts` uses the actual pinned Node fetch implementation with a 150ms timeout. A complete 14-byte response is consumed; a timeout before headers is wrapped; a timeout after headers and partial body is not. The final expected-classification assertion fails. The fault server and environment changes belong only to the isolated probe process. The running app and real sidecar configuration are untouched.

The native preview endpoint was not subjected to this injected fault: its status/log mapping is established by source, not a separate endpoint reproduction. This is not evidence of a real 120-second Gotenberg incident, partial artifact delivery, content loss, authorization failure or capacity exhaustion. The output is assigned only after successful conversion.

The same probe rejects P045's post-import cache-setting hypothesis: `collectSystemFacts()` resolves after the probe changes the cache environment value, because the getter returns a constant validated at module evaluation. A malformed value before the first import is a separate configuration-failure case, not a demonstrated running-panel defect. Three other readers left open by that author response are not accepted findings.
