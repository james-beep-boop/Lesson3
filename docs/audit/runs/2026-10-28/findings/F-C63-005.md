# F-C63-005 — consecutive links appear away from the visible caret

- Source: `6e75a173e822e4c4be42821b0a4af48ca457bd36`.
- Severity: Low; visible insertion-placement defect.
- Evidence: actual native lesson form in Chromium and WebKit; both expected-placement assertions fail.
- Review: Haiku P068 → Sol source/browser critique → fresh-context Haiku response → Sol scope check.
- Status: audit only; no fix.

In a lesson's learner-experience field, type `Alpha Beta`, place the caret after `Alpha`, insert `https://example.invalid/one`, then immediately insert `https://example.invalid/two` without moving the caret. The test verifies that the live caret is before trailing `Beta` before opening the second dialog. Chromium places the second address after `Beta`; WebKit places it before the first address. The two engines fail different ordering assertions.

`LinkedTextarea/index.tsx:97` inserts at a remembered ref, while lines101–104 focus and set the live selection after insertion. `rememberAsTarget` updates the ref through focus/key/mouse/select event capture. The divergence is reproduced; the exact event ordering and sole causal responsibility of the ref are not instrumented. It would be incorrect to say no selection handler exists, or that both engines produce the same wrong position.

Reproduction: the isolated audit browser case `audit: consecutive link insertions use the visible caret in both browsers`. Both URLs and surrounding words remain visible. This does not establish loss of saved data, a wrong link target or an authorization problem. Manually moving the caret between insertions and slower repeated workflows were not tested. The review's proposed fix is untested and is not part of this audit.
