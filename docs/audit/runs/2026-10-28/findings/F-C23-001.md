# F-C23-001 — Signup accepts a password that sign-in rejects

- Source: `6e75a173e822e4c4be42821b0a4af48ca457bd36`.
- Severity: Low; account usability edge, not a session bypass.
- Evidence: locally reproduced over real HTTP with a trusted fixture approval; original-author recheck retained the narrowed claim.
- Known status: new audit finding. Disposition: report only.

`endpoints/login.ts:29` rejects an all-whitespace password before calling Payload's credential comparison. Native signup accepts an eight-space password. An approved account created that way cannot sign in with its accepted password.

Reproduction: `app/tests/audit/blank-password.ts`. Positive control: ordinary password signup201, trusted verification, login200. Whitespace case: signup201, trusted verification, identical password login400. The assertion fails and fixtures are deleted. SMTP is confined to the disposable capture service; no messages go outside the audit target. “Approved” here means trusted fixture verification, not a claim to have driven the human approval UI.

Review: Haiku P011 lead → Sol source and HTTP critique → Haiku response in `reviews/F-C23-001-author-response.md`. The author correctly distinguishes blank-input rejection from a wrong-password result. The general acceptance assertion permits a future signup-side rejection; it is evidence for this baseline, not an implementation-specific fix test. Password-reset behaviour is outside this particular finding.
