# F-C63-006 — reset-link copy lacks its fallback on plain HTTP

- Fixed source: `6e75a173e822e4c4be42821b0a4af48ca457bd36`.
- Severity: Low; supported school-interface usability.
- Evidence: actual native Accounts panel, Chromium and WebKit, non-localhost HTTP origin.
- Review: Haiku P072 → Sol source/browser critique → fresh-context Haiku response → Sol check.
- Status: audit only; no fix.

In Manage → Users → Accounts, a Site Administrator reveals a synthetic teacher's reset link, then presses Copy link. Both browsers report `isSecureContext=false` and no `navigator.clipboard`. The handler at `Manage/UsersPanel.tsx:206–211` throws synchronously while accessing `writeText`; its promise catch is never attached. Both browser tests observe one matching TypeError and no intended “select and copy the link below” message.

Reproduction: isolated browser case `audit: reset-link copy gives manual instructions on a plain HTTP school origin`. The generated reset link remains in a visible selectable read-only input; manual copying remains possible. No token or private credentials are included in the public result. Permission denial when an existing Clipboard API rejects is a different path and is already caught; this reproduction does not test that path. No authorization or token-disclosure finding follows.
