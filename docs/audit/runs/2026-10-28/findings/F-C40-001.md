# F-C40-001 — padded sub-strand identity creates duplicate plans on re-import

- Severity: **Medium**; input-dependent data-integrity defect.
- Exposure: current supported import/upload path, restricted to trusted operator/Site Administrator input; no anonymous write claimed.
- Known status: new audit finding. The trimming code dates to July; this is not attributed to the recent simplification PRs.
- Source: `6e75a173e822e4c4be42821b0a4af48ca457bd36`.
- Evidence: source-confirmed and reproduced on disposable local Postgres, production-mode configuration. No deployed-server reproduction.
- Review: Haiku source lead P003; independent Sol source/runtime check confirms it. Author response in small packet P011 retained the finding, with speculative ancestry/edit-path consequences excluded from the reproduced scope. Required author → opposite-family critique → author response completed.
- Disposition: report only. No implementation fix or fix PR.

## Scenario and cause

Import a schema-valid nonempty `META.substrand_id` containing leading/trailing spaces. Import a revised file with exactly that same ID again. `ingest/index.ts:110–113` trims the lookup identity, while `findExistingPlan` at `:135–136` queries `meta.substrand_id` by exact equality. `toBundle.ts:48` retains the raw META object, and the native text field has no trimming hook. Consequently the stored padded value does not match the trimmed lookup, including inside the write locks.

Expected: both imports belong to the same plan, with a new major version for revised content. The same nonempty identifier must not become a new identity on every import. Actual: both imports create distinct 1.0.0 Official plans. This separates history and can leave teachers seeing duplicate lesson plans. Existing content is not overwritten; no data loss is claimed.

## Reproduction and controls

`app/tests/audit/identity-whitespace.ts` seeds its own synthetic subject/grade, runs the real ingestUploadItems preview/confirmation flow and removes all its rows in finally. It uses the isolated integration database, separate from browser tests.

- Plain ID `77.1`: first import 1.0.0, revised import 2.0.0, same plan.
- Padded ID ` 77.2 `: two different plans, both 1.0.0; the stored ID remains padded.
- The explicit same-plan assertion fails against the unchanged baseline. Reproduction output and failing exit are retained privately. No implementation was changed.

Run with the pinned dependency wrapper, an approved disposable DB in DATABASE_URI and NODE_ENV=production: `npx tsx tests/audit/identity-whitespace.ts`. Do not run against an installation. The expected exit is nonzero while this defect exists.

A later fix needs a consistent identity-normalization/rejection policy covering existing padded records, plus regression and wire coverage. It is outside this audit.
