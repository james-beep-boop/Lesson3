# F-C63-001 — Deleting a human actor enables the system-update notice

- Source: `6e75a173e822e4c4be42821b0a4af48ca457bd36`.
- Severity: Low; functional provenance edge, not an access-control defect.
- Evidence: locally reproduced on real PostgreSQL with native authorized deletion; original-author recheck retained the narrowed claim.
- Known status: new audit finding. Disposition: report only.

`fields/officialChange.ts` stamps a person's id on a manual Official pointer change. `lib/aresReleasePresentation.ts:31` suppresses the system notice while that id is non-null. Deleting the person clears the foreign key with SET NULL while preserving the date and prior version. The helper then produces a system-update notice, contrary to SPEC §6's “never for a human change” condition. The lesson page consumes that helper's result.

Reproduction: `app/tests/audit/notice-actor-deletion.ts`, on a separate migrated cases database. Two verified Site Administrators are seeded; one manually promotes an ARES snapshot; the other performs an authorized native delete of that actor. Before deletion: actor recorded, notice null. After deletion: actor null, same timestamp, notice present. The expected-null assertion fails; fixtures are removed. The displayed release/date and previous version remain factual. No data loss, access bypass or overwritten history is claimed.

Review: Haiku P030 lead → Sol source/caller and runtime critique → Haiku response in `reviews/F-C63-001-author-response.md`. Retained as Low. A later fix needs a provenance representation that survives actor deletion; this audit changes no schema or behaviour.
